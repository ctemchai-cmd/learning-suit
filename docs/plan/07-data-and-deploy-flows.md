# 07 — ตัวจำลองการไหล: การเก็บข้อมูล และการ Deploy

> **สถานะ (2026-09-25):** ผู้สอนยืนยันแล้ว และสร้างครบทั้งสองตัว — ตัวจำลองการเก็บข้อมูล 4 ขั้น (M8.1–M8.2) และตัวจำลอง Deploy 4 ขั้น (M8.3–M8.4) ดูหลักฐานที่ [แผนส่งมอบ](06-delivery-and-acceptance.md)

## 1. เป้าหมายการสอน

ผู้สอนต้องการสอน**หลักการ** ไม่ใช่โค้ด: นักเรียนต้องเห็นว่าข้อมูลหรือโค้ด**ไหล**จากไหนไปไหน ผ่านอะไร หยุดที่ไหน และทำไม บทเรียนต่อจาก Git ตามเส้นเรื่องเดียว:

```
Git (ทำแล้ว) → การเก็บข้อมูล → Supabase (ในฐานะบริการที่เก็บข้อมูลให้) → เปิดเว็บในเครื่อง → ขึ้น Vercel → ภาพรวมทั้งระบบ
```

**ไม่ทำ:** SQL, โค้ด supabase-js, คำสั่ง terminal, การเชื่อมบริการจริง (Supabase/Vercel/GitHub) ทุกอย่างเป็นการจำลองแบบ deterministic ใช้ได้ offline, Undo ได้ และเล่นซ้ำได้ ส่วนของจริงผู้สอน demo ผ่าน dashboard ของ Supabase/Vercel แยกต่างหาก แล้วกลับมาชี้บนกระดาน

## 2. ภาษาภาพร่วม: การไหล (Flow)

ตัวจำลองทั้งสองใช้ภาษาภาพชุดเดียวกัน และใช้ engine เดียวกัน (§5)

| องค์ประกอบ | ความหมาย | ตัวอย่าง |
|---|---|---|
| **กล่อง (node)** | อุปกรณ์ บริการ หรือที่เก็บข้อมูล | คอมพิวเตอร์ A, ฐานข้อมูล, GitHub, Vercel |
| **ท่อ (pipe)** | เส้นทางที่ข้อมูลวิ่งได้ | คอมพิวเตอร์ → อินเทอร์เน็ต → ฐานข้อมูล |
| **ก้อนข้อมูล (packet)** | สิ่งที่กำลังเดินทาง มีป้ายสั้น | “ออเดอร์: ลาเต้”, “โค้ดรุ่นใหม่”, “🔑 กุญแจ” |
| **ด่าน (gate)** | จุดตรวจบนท่อ ผ่าน ✓ เขียว / ไม่ผ่าน ✗ แดงแล้วก้อนเด้งกลับ | กฎสิทธิ์, ชนิดข้อมูล, Build |
| **คำบรรยาย** | หนึ่งบรรทัดใต้ภาพ บอกจังหวะปัจจุบัน | “2/4 ด่านกฎสิทธิ์: B ขอดูออเดอร์ของ A → ไม่อนุญาต” |

**แอปรอข้อมูล:** ตั้งแต่แอปส่งอะไรออกไป (หรือมีคำตอบกำลังวิ่งมาหา) จนก้อนนั้นถึง แอปขึ้นวงหมุน “กำลังโหลด…” / “กำลังบันทึก…” (`waitingAt`) รายการบนจอจึงเปลี่ยนพร้อมกับที่ก้อนถึงพอดี ใช้กับคอมพิวเตอร์ทุกขั้น และ browser ในเครื่อง/คอมเพื่อนของตัวจำลอง Deploy

**การควบคุมของผู้สอน (แผงขวา):** ปุ่มสถานการณ์ของขั้นนั้น (เช่น “ลูกค้า A สั่งลาเต้”), เล่นต่อเนื่อง / **ทีละจังหวะ** (ปุ่ม “ถัดไป ▶” เพื่อหยุดอธิบายแต่ละช่วง), ความเร็ว ช้า/ปกติ และเล่นซ้ำ ระหว่างเล่นยังไม่แก้ document; จบจังหวะสุดท้ายผลลัพธ์ (แถวใหม่, deployment ใหม่) บันทึกเป็น **transaction เดียว Undo ได้** เหมือน action ของ Git

**ไอคอนแทนอีโมจิ (feedback 2026-09-26):** บนกระดานใช้ไอคอน Lucide วาดเป็น Konva `Path` (`src/features/flow/icon-paths.ts` สร้างด้วย `node scripts/build-icon-paths.mjs` คมทุกซูมและติดไปกับ Export) ในแผงใช้ `lucide-react`; ของที่ส่งไปกับแพ็กเก็ตเป็นข้อมูลมีชนิด (`CarriedLine{kind,text}`) กระดานเลือกไอคอน/สีจากชนิด ไม่ฝังอีโมจิในข้อความ; log เก่าที่ขึ้นต้นด้วยอีโมจิถูกตัดออกตอนแสดง; สัญลักษณ์ข้อความ ✓ ✗ ↔ ↕ ✎ ↻ ยังใช้ได้

**แผงขวาต้องคลีน (feedback 2026-09-26):** หัวข้อสั้นหนึ่งบรรทัดต่อเรื่อง, ตัวเลือกเป็น segmented control, ปุ่มสถานการณ์มีไอคอนและคำสั้น (ปุ่มแรกที่ควรลองเป็นสีน้ำเงิน), ฟอร์มหลายแบบแยกเป็นแท็บ (เช่น เพิ่ม/ดู/แก้/ลบ) ไม่มีคำอธิบายซ้ำกับกระดาน — คำอธิบายอยู่ในแถบคำบรรยายบนกระดาน, คำอธิบายขั้นอยู่ใน tooltip ของ dropdown; แถบควบคุมการเล่นย่อเหลือ “ต่อเนื่อง/ทีละจังหวะ” + ปุ่มช้า และแสดงความคืบหน้า/ถัดไป/ข้าม/เล่นซ้ำเฉพาะตอนกำลังเล่น เมนูที่สั่งหมุนเวียนเองจึงไม่ต้องเลือก

**ค่อยๆ แสดงทีละส่วน (progressive reveal, เพิ่ม 2026-10-15):** ตัวเลือกต่อ widget (ปิดเป็นค่าตั้งต้น) ให้ครูเผยฉากทีละส่วนระหว่างอธิบาย เหมือนไล่วาดบนไวต์บอร์ด ใช้กับตัวจำลองทั้งห้าชนิด (Git, SSH, Deploy, Data, AI) ทุกขั้นมี 3–6 part: Deploy `deployParts` / Data `dataParts` / AI `aiParts` อยู่ข้าง layout ของแต่ละตัว (ชิ้นที่วาดแมปเข้า part ด้วยตาราง piece→part, ท่อมี `part` ของตัวเอง = ปลายที่อยู่หลัง); `frame-walk.ts` เป็นตัวช่วยของ unit test ที่รัน reducer เพื่อหา spot ที่เฟรมใช้ (spot ที่ขั้นนั้นไม่วาด เช่น `.env.local` ในขั้น overall ไม่มี part: ก้อนวิ่งจึงถึงทันทีเหมือนเดิม)
- **ข้อมูล:** `reveal?: number` บน widget node = จำนวน part ที่แสดงแล้ว (ไม่มี = โหมดปิด แสดงทั้งหมด; schema เป็น int 0–`REVEAL_MAX`=12 ทุกชนิด widget เอกสารเก่าไม่กระทบ) อยู่ใน document จึงซิงก์กับห้องวาดร่วมและ Undo ได้
- **Part:** แต่ละขั้น/มุมมองมีรายการ `RevealPart { id, label }` เรียงตามลำดับที่เผย (label ภาษาไทย 3–6 อัน) เขียนเป็นฟังก์ชันบริสุทธิ์ข้างโค้ด layout ของตัวจำลองนั้น (`sshParts`, `gitParts` …) ฟังก์ชันช่วยทั้งหมดอยู่ที่ `src/domain/document/reveal.ts`
- **วาด:** part ที่ซ่อน “ไม่วาดเลย” (ที่ว่างเปล่า) ตำแหน่งต้องไม่ขยับเมื่อ part ปรากฏ (layout เหมือนตอนเต็ม) ท่อ/ลูกศร/ป้ายของ part ที่ซ่อนซ่อนด้วย; ลูกศรระหว่างสอง part โผล่พร้อม part ที่อยู่หลัง; ชื่อ widget กรอบและแถบคำบรรยายคงอยู่; Export วาดเหมือนกระดาน; ปุ่ม/ช่องแก้ที่ซ้อนบนกระดาน (DOM overlay) ของ part ที่ซ่อนก็ไม่แสดง
- **ควบคุม:** คอมโพเนนต์เดียว `RevealControls` (`flow-panel-parts.tsx`) ในแผงของตัวจำลอง: สวิตช์ “ค่อยๆ แสดงทีละส่วน”, ปุ่ม “แสดงส่วนถัดไป: <ชื่อ part> (k/N)”, “แสดงทั้งหมด”, “ซ่อนใหม่” ทุกครั้งที่กดเป็น transaction ของตัวเอง Undo ได้; เปลี่ยนขั้นบทเรียนรีเซ็ตเป็น 0 ใน transaction เดียวกับการเปลี่ยนขั้น (สลับ GitHub/GitLab ไม่รีเซ็ต)
- **action เปิด part ที่ต้องใช้เอง:** ตอนกดปุ่มสถานการณ์ ถ้าแอนิเมชันหรือสถานะแตะ part ที่ยังซ่อน จะเผยในการ transaction เดียวกับ action (จำนวนเพิ่มถึง part ท้ายสุดที่ต้องใช้ ไม่เคยลด) ตัวจำลองแบบ flow ใช้ `partsOfFrames(frames, partOfSpot, along)` แปลง spot ของ hop/mark เป็น part id (+ part ที่ก้อนวิ่งผ่าน เช่นด่าน) ส่วน Git ใช้ `gitActionParts(view, action)`
- **โหมดสอน:** PageDown และปุ่ม “สไลด์ถัดไป” เผย part ถัดไปของ widget บนสไลด์ที่เปิดโหมดและยังเหลือ part (เลือกอยู่ก่อน ไม่เช่นนั้นตัวบนสุด — `pickRevealTarget` ใน `src/features/editor/widget-reveal.ts`) เมื่อไม่เหลือจึงไปสไลด์ถัดไป; PageUp เหมือนเดิม

**วิธีเพิ่ม part ให้ตัวจำลองใหม่ (Deploy/Data/AI):** (1) เขียน `<name>Parts(view, …): RevealPart[]` ข้าง layout (id คงที่ ลำดับ = ลำดับเผย) และ `<name>PartOfSpot(view, spot)` (ทุก spot ที่เฟรมใดใช้ต้องแมปเป็น part ของขั้นนั้น; สำหรับ flow) (2) ใน widget view ทำ `const shows = partFilter(parts, node.reveal)` แล้วครอบทุกชิ้นที่วาดด้วย `shows("<id>") && …` พร้อมท่อ/ป้ายของมัน ห้ามเปลี่ยนตำแหน่ง; ถ้ามี DOM overlay ให้ซ่อนด้วย (3) ในแผงใส่ `<RevealControls node parts slideId writable transact />` ใน `run(action)` ใช้ `revealForParts(parts, node.reveal, partsOfFrames(...))` ใส่ลง node เดียวกับ state ผ่าน `withReveal(node, reveal)` และใน `changeView` ใช้ `withReveal(node, revealOnStepChange(node.reveal))` (4) เพิ่ม case ใน `widgetRevealParts` (`widget-reveal.ts`) เพื่อให้โหมดสอนรู้จัก (5) เขียน unit test: รายการ part ต่อขั้น (ไม่ว่าง id ไม่ซ้ำ), ทุก spot ที่ reducer ใช้ (หาจากการรัน reducer ไม่ใช่จาก layout) แมปเป็น part พร้อม planted omission, และ action → part

**กติกาที่ยกมาจากตัวจำลอง Git:** ขั้นบทเรียนเลือกจาก dropdown แต่ละขั้นเพิ่มแนวคิดใหม่เรื่องเดียว; แก้ข้อมูลบนกระดานได้โดยตรง; แผงขวามีแค่ปุ่มและไฮไลต์ “ทำต่อ”; ความผิดพลาดที่พบบ่อยจำลองได้และ**ต้องมีทางออกเสมอ**; Export เป็นภาพนิ่งของสถานะล่าสุด (ไม่มีก้อนที่กำลังวิ่ง); ป้ายเล็ก “ใน Supabase/Vercel เรียกว่า …” เชื่อมไปของจริงโดยไม่ต้องเห็นโค้ด

## 3. ตัวจำลองการเก็บข้อมูล (ธีมแอปรายรับรายจ่าย)

ข้อมูลตัวอย่าง: ตาราง **หมวด** (ชื่อ, ประเภท รายรับ/รายจ่าย, ใช้อยู่) เช่น เงินเดือน (รายรับ) อาหาร เดินทาง ช้อปปิ้ง (รายจ่าย), **ผู้ใช้** (สมชาย = คอม A, สมหญิง = คอม B) และ **รายการ** (เจ้าของ → ผู้ใช้, หมวด → , จำนวนเงิน) แก้ทุกช่องบนกระดานได้ จำนวนเงินแสดงเป็นบาทมีจุลภาคคั่นหลัก (เช่น 25,000 บาท) รายรับสีเขียว รายจ่ายสีแดง

ทุกขั้นวาดคอมพิวเตอร์เป็น **จอคอมตั้งโต๊ะ** (ขอบจอ + คางจอ + ขาตั้งและฐาน) หน้าจอแสดง UI ของแอป คอม B คือ “อีกเครื่องของเรา” (เช่น คอมที่บ้านกับคอมที่ทำงาน) หรือเครื่องของอีกคนในขั้นสุดท้าย

> เวอร์ชันเก่า (ธีมร้านกาแฟ, `version: 1`): เอกสารที่บันทึกไว้จะถูกแทนที่ด้วยข้อมูลตั้งต้นใหม่ตอนเปิด (เป็นข้อมูลสาธิต) ตำแหน่ง ขนาด ขั้น และ reveal ของกล่องยังอยู่ครบ

### ขั้น 1 — ข้อมูลเก็บที่ไหน

คอมแต่ละเครื่องวาดเป็น **จอคอม** ที่หน้าจอเป็น **หน้าต่างแอป** (แถบชื่อ + ไอคอนรีเฟรช ↻) ซึ่งมี **ความจำของแอปอยู่ในกรอบของแอป** ส่วน “เก็บในเครื่อง” อยู่ใต้ขาตั้ง เป็นที่เก็บของคอมเครื่องนั้นแต่อยู่นอกแอป รีเฟรช = แอปเริ่มใหม่: ↻ หมุน หน้าจอว่าง ความจำของแอปลอยหาย แล้วจึงโหลดใหม่ตามวิธีเก็บ

กล่อง: คอม A, คอม B, ฐานข้อมูล (cloud) สถานการณ์ “คอม A บันทึกค่ากาแฟ 60 บาท” เล่นได้สามแบบ:

```
เก็บในแอป        A: [ค่ากาแฟ 60 บาท] ─ รีเฟรช → 💨 หาย                  ✗
เก็บในเครื่อง A   A: [ค่ากาแฟ 60 บาท]    B เปิดดู → (ว่าง) มองไม่เห็นของ A  ✗
เก็บในฐานข้อมูล   A ──รายการ──▶ [ฐานข้อมูล] ──รายการ──▶ B                ✓ ทุกเครื่องเห็นเหมือนกัน
```

### ขั้น 2 — ตาราง

ฐานข้อมูลขยายเป็นตาราง **หมวด**: 1 แถว = 1 หมวด, 1 คอลัมน์ = 1 เรื่อง (ชื่อ / ประเภท / ใช้อยู่), ทุกแถวมีเลข ID ไม่ซ้ำ และแต่ละคอลัมน์มีชนิดข้อมูล (ข้อความ / รายรับ-รายจ่าย / ใช่-ไม่ใช่) สถานการณ์สี่แบบแสดงเป็นการไหล:

- **เพิ่ม** (Create): ก้อนวิ่งเข้าไป แถวใหม่ค่อยๆ ปรากฏ
- **ดู** (Read “ดูหมวดทั้งหมด”): สำเนาแถววิ่งกลับไปที่คอม A ตารางเดิมไม่เปลี่ยน
- **แก้** (Update): ก้อนวิ่งไปหยุดที่ช่องเดียว ช่องนั้นเรืองแสงเป็นค่าใหม่
- **ลบ** (Delete): แถวจางหายไป
- ใส่ประเภทเป็น “ออม” (ไม่ใช่รายรับ/รายจ่าย): ก้อนติดด่าน “ชนิดข้อมูล” สีแดงแล้วเด้งกลับ ตารางไม่เปลี่ยน

### ขั้น 3 — เชื่อมตาราง (อย่าก๊อปข้อมูลซ้ำ)

วางสองวิธีคู่กัน แล้วเล่นสถานการณ์ “เปลี่ยนชื่อหมวด” (เช่น อาหาร → อาหารและเครื่องดื่ม):

```
ก๊อปชื่อหมวดไว้ในทุกรายการ                อ้างถึงด้วย ID
รายการ 2: "อาหาร"                         รายการ 2 ─┐
รายการ 3: "อาหาร"   ← ต้องแก้ทุกแถว         รายการ 3 ─┴─▶ หมวด #2 "อาหาร" ← แก้ที่เดียว
ลืมแก้บางแถว → ชื่อขัดกัน ✗ (สีแดง)         ทุกรายการตามเส้นไปเห็นชื่อใหม่ ✓
```

เพิ่มรายการใหม่ได้ (เก็บเลขหมวด + ก๊อปชื่อหมวดไว้ด้วย) หมวดที่ไม่ได้ใช้อยู่เลือกบันทึกไม่ได้ ลบหมวดที่ยังมีรายการ: ก้อนติดด่าน “ยังมีข้อมูลอ้างถึง (2 รายการ)” พร้อมทางออก: ลบรายการของหมวดก่อน หรือยกเลิก

### ขั้น 4 — ใครเห็นอะไร (สิทธิ์)

คอม A และ B login เป็นคนละคน (สมชาย / สมหญิง) รายการรายรับรายจ่ายเป็นข้อมูลการเงินส่วนตัว คำขอทุกครั้งต้องผ่านด่าน **กฎสิทธิ์** ก่อนถึงตาราง:

```
B: ขอดูรายการ ──▶ [ด่านกฎสิทธิ์: เห็นเฉพาะของตัวเอง] ──▶ รายการของ B ✓
                                                  รายการของ A ✗ (ถูกกรองที่ด่าน)
หมวด = ข้อมูลสาธารณะ ทุกคนเห็น
ปิดกฎสิทธิ์ → รายรับรายจ่ายของ A วิ่งถึง B เป็นสีแดง “ข้อมูลรั่ว”
```

### ป้ายเชื่อมกับ Supabase (ไม่มีโค้ด)

ฐานข้อมูล = **Supabase (Postgres)**, ตาราง = **Table Editor**, คนที่ login = **Authentication**, กฎสิทธิ์ = **RLS Policy**, ท่อจากแอปถึงฐานข้อมูล = **API** ผู้สอนเปิด dashboard ของ Supabase ให้เห็นว่าเป็นสิ่งเดียวกัน (สร้างตาราง/นโยบายได้จากหน้าเว็บโดยไม่เขียนโค้ด)

## 4. ตัวจำลองการ Deploy

กล่อง: เครื่องเรา (โค้ด), เซิร์ฟเวอร์ในเครื่อง, GitHub, Vercel (ด่าน Build → Deploy), อินเทอร์เน็ต, คอมพิวเตอร์เพื่อน (จอคอมตั้งโต๊ะ) และในขั้นท้าย Supabase ไม่แสดงคำสั่ง แสดงเป็นปุ่มภาษาคน เช่น “เปิดเว็บในเครื่อง”, “ส่งโค้ดขึ้น GitHub”

### ขั้น 1 — เปิดเว็บในเครื่อง (Local)

```
[โค้ด] ──▶ [เซิร์ฟเวอร์ในเครื่อง] ──▶ [browser ในเครื่อง: localhost] ✓
[คอมเพื่อน] ──✗── ท่อขาด “ที่อยู่นี้มีแค่ในเครื่องเรา”
แก้โค้ด → ก้อน “โค้ดใหม่” วิ่งไปเซิร์ฟเวอร์ → หน้าเว็บในเครื่องเปลี่ยนทันที
```

### ขั้น 2 — กุญแจในเครื่อง (.env.local)

```
[.env.local 🔑] ──กุญแจ──▶ [เซิร์ฟเวอร์ในเครื่อง] ──🔑 ออเดอร์──▶ [ฐานข้อมูล]  ✓
เอากุญแจออก → เซิร์ฟเวอร์หากุญแจไม่เจอ → ต่อฐานข้อมูลไม่ได้ ✗
```

เห็นภาพ env ในเครื่องอย่างเดียวก่อนขึ้น Vercel: ไฟล์ลับอยู่ในเครื่อง เซิร์ฟเวอร์อ่านกุญแจทุกครั้งที่ต้องคุยกับฐานข้อมูล สลับ “มีกุญแจ / ไม่มี” ได้จากแผง

### ขั้น 3 — ขึ้น Vercel

```
[เครื่องเรา] ──โค้ด──▶ [GitHub] ──▶ [Vercel: ด่าน Build ✓ → Deploy] ──▶ [URL สาธารณะ] ◀── คอมเพื่อน ✓
```

- ทุกครั้งที่ส่งโค้ดขึ้น GitHub จะเกิด deployment ใหม่ (D1, D2 …) หน้าตาเหมือนรายการ commit และมีป้าย “ใช้งานจริง (Production)” เหมือนป้าย main
- **Build ล้ม:** ก้อนหยุดที่ด่าน Build เป็นสีแดง แต่**เว็บเดิมยังออนไลน์อยู่** (ป้าย Production ไม่ย้าย) เป็นบทเรียนสำคัญ
- **ย้อนรุ่น (Rollback):** ย้ายป้าย Production กลับไป deployment ก่อนหน้า คอมเพื่อนเห็นรุ่นเก่าทันที

### ขั้น 4 — กุญแจบน Vercel

```
[เครื่องเรา: 🔑 กุญแจฐานข้อมูล] ──โค้ด──▶ GitHub      (กุญแจไม่ถูกส่งไปด้วย: ติดด่าน “ไฟล์ลับ”)
[Vercel: ตั้งค่า 🔑] ← ผู้สอนต้องใส่เองในหน้าตั้งค่า
ลืมใส่ → เว็บออนไลน์ แต่ท่อ Vercel → Supabase ขาด “ต่อฐานข้อมูลไม่ได้” ✗
ใส่แล้ว Deploy ใหม่ → ต่อได้ ✓
```

### ขั้น 5 — ภาพรวมทั้งระบบ

คอมเพื่อนสั่งกาแฟบนเว็บจริง: คอม → Vercel → Supabase (ด่านกฎสิทธิ์) → ตารางออเดอร์ → ผลวิ่งกลับ รวมทุกบทเรียนไว้ในภาพเดียว ตรงกับที่นักเรียนจะทำจริงและตรงกับแอปนี้เองที่ใช้ Vercel + Supabase

เพราะทุกขั้นใช้ state เดียวกัน การทดลองในขั้นก่อน (เช่น ทำโค้ดพัง หรือยังไม่ใส่กุญแจ) จะติดมาด้วย ขั้นนี้จึงมีปุ่ม **“เตรียมเว็บให้พร้อม”** ที่แก้โค้ด + ใส่กุญแจ + Deploy ต่อกันเป็น flow เดียว (Undo ได้ในครั้งเดียว) ส่วนขั้นกุญแจลับมีการ์ดแก้โค้ดเมื่อโค้ดยังพังค้างอยู่

## 4c. ตัวจำลอง SSH (เพิ่ม 2026-10-05)

ผู้สอนใช้ภาพเปรียบ **เครื่องสแกนลายนิ้วมือหน้าประตูตึก** สอนว่า SSH key คืออะไรและทำไม GitHub ต้องใช้ — node `ssh-simulator` ใช้ flow engine เดียวกับ Deploy (กรอบ 1120×680, ก้อนข้อมูลบนท่อ, คำบรรยายประโยคเดียว, เล่นต่อเนื่อง/ทีละจังหวะ/ช้า) — แถบ “เปรียบเทียบ” ใต้กระดานถูกเอาออก (2026-10-05 ครูว่ารก) การเปรียบเทียบอยู่ในป้ายของกุญแจแต่ละแถวและคำบรรยายแทน

**ปรับ 2026-10-05 ตาม feedback ครู (3 ข้อ):** (1) รวมขั้นเดิม 1–4 เป็นขั้นเดียว “เชื่อม GitHub ด้วย SSH (ทีละขั้น)” ที่ฉากไม่เปลี่ยน และแผงเป็นการ์ดเลขลำดับแบบ Git panel; (2) ตัด `known_hosts`/host key ทิ้งทั้งหมด (ครูว่างง); ต่อมาย่อคำอธิบายการ์ด/ปุ่มให้เหลือบรรทัดเดียว (ครูว่ายาวไป); (3) โชว์ความสัมพันธ์ `id_ed25519` → `id_ed25519.pub` ว่าสร้างทางเดียว ย้อนกลับไม่ได้ เพื่อให้เห็นว่าทำไม .pub ที่ถูกคัดลอกไปไร้ประโยชน์

| ของจริง | ในภาพเปรียบ | บนกระดาน |
|---|---|---|
| กุญแจลับ `~/.ssh/id_ed25519` | นิ้วจริง: **ใช้ทำผลสแกน** อยู่กับเรา ไม่ส่งให้ใคร | แถวในโฟลเดอร์ `~/.ssh` ของเครื่อง A (ไม่เคยเป็นสิ่งที่วิ่งไปบนท่อ) |
| กุญแจสาธารณะ `id_ed25519.pub` | ลายนิ้วมือที่ลงทะเบียนไว้ที่ประตู: **ใช้ตรวจผลสแกนได้อย่างเดียว** แจกได้ | แถว `.pub` (ลูกศร “สร้างมาจากกุญแจลับ · ย้อนกลับไม่ได้ ✗” จากแถวกุญแจลับ) และแถวใน GitHub → Settings → SSH keys |
| GitHub | ตึกที่มีเครื่องสแกน | ด่าน “ด่านสแกนนิ้ว” (Gate) กลางท่อ + การ์ด repo, รายการกุญแจ |
| เชื่อมต่อ | แตะนิ้ว: ประตูส่ง “เลขสุ่มใช้ครั้งเดียว” (= ขอแตะนิ้วสดๆ ตอนนี้ กันผลสแกนเก่ามาใช้ซ้ำ) เครื่องประทับด้วยกุญแจลับได้ “ผลสแกน” (ลายเซ็น) ประตูใช้ .pub ที่ลงทะเบียน **ตรวจ** ผลสแกนนั้น | เฉพาะ “ผลสแกน” วิ่งกลับ (การ์ดบอกว่า “ไม่มีกุญแจลับในก้อนนี้”) |

### สวิตช์ GitHub ↔ GitLab (เพิ่ม 2026-10-15)

ครูจะสอน GitLab ให้ทีม: node มีฟิลด์ `host?: "github" | "gitlab"` (ไม่มี = GitHub, เอกสารเก่าเปิดได้เหมือนเดิม) ชื่อ/ที่อยู่ SSH/หน้าวางกุญแจ/ข้อความต้อนรับมาจาก `domain/hosting.ts` ที่เดียว (ใช้ร่วมกับตัวจำลอง Git) แผงมีปุ่มสลับ “GitHub | GitLab” บนสุด (เป็น transaction ของตัวเอง เลิกทำได้ และล้างหน้าจอ terminal เพราะยังโชว์คำตอบของเว็บเก่า) ทุกอย่างที่ออกชื่อเว็บเปลี่ยนตาม: ชื่อกล่อง, รายการกุญแจ (“Settings → SSH keys” / “Preferences → SSH Keys”), คำสั่ง `ssh -T git@gitlab.com`, remote ของ push, คำตอบ “Welcome to GitLab, @you!”, คำบรรยาย, ข้อความผลลัพธ์, ปุ่ม “ใส่ .pub ใน GitLab”, ชื่อขั้น “เชื่อม GitLab ด้วย SSH” `applySshAction(state, action, view, host?)` รับ host เป็นพารามิเตอร์ (ไม่อ่านค่า global, frames ยัง deterministic) ต่างกันแค่ถ้อยคำ: state/outcome/hop เหมือนกันทุกประการ

### ขั้น “เชื่อม GitHub ด้วย SSH” (`setup`)

ฉากเดียวตลอด: เครื่อง A (`~/.ssh`, terminal) ↔ ด่านสแกนนิ้ว ↔ GitHub (repo + รายการ SSH keys) แผงเป็นการ์ด 4 ใบ ใบที่ “ทำต่อ” ไฮไลต์ตามสถานะ (ยังไม่ได้ทำอะไร → ①, ไม่มีกุญแจ → ②, ยังไม่ลงทะเบียน → ③, ลงทะเบียนแล้ว → ④) และคำบรรยายใต้กระดานตอนว่างก็ตามสถานะเดียวกัน

1. **ลอง push ก่อน** — [ลอง git push] ก้อนวิ่งไปติดด่านแดง “GitHub: คุณคือใคร? ไม่มีลายนิ้วมือที่ลงทะเบียนไว้ ✗ Permission denied (publickey)” (เป็นการลองดู ไม่บังคับ)
2. **สร้างคู่กุญแจ** — แสดงคำสั่ง `ssh-keygen -t ed25519 -C "you@example.com"` [สร้างกุญแจ] 4 จังหวะ: รันคำสั่ง → ได้ `id_ed25519` (กุญแจลับ = นิ้วจริง) → **คำนวณ .pub ออกมาจากกุญแจลับ** (ก้อนวิ่งจากแถวกุญแจลับไปแถว .pub: “ทางเดียว จาก .pub ย้อนกลับไปหากุญแจลับไม่ได้ เหมือนจากภาพลายนิ้วมือ เสกนิ้วจริงไม่ได้”) → ได้ `.pub` (ลายนิ้วมือ ใช้ตรวจผลสแกนได้อย่างเดียว) สร้างซ้ำ = noop
3. **ลงทะเบียน .pub** — [ใส่ .pub ใน GitHub] เปิดไฟล์ .pub → การ์ด `ssh-ed25519 AAAAC3Nza…` วิ่งไปรายการ SSH keys (เหมือนแตะนิ้วลงทะเบียนที่ประตูครั้งเดียว) ยังไม่มีกุญแจ = `rejected`
4. **เชื่อมต่อ** — [ssh -T git@github.com] [git push] 6 จังหวะ: ขอเข้า → ขอแตะนิ้ว (เลขสุ่มใช้ครั้งเดียว) → ประทับในเครื่อง (แถวกุญแจลับสว่าง “ตัวนิ้วไม่ออกไปไหน”) → ผลสแกนวิ่งกลับ → ประตูใช้ลายนิ้วมือ (.pub) ที่ลงทะเบียนไว้ตรวจผลสแกนที่กุญแจลับทำขึ้น ✓ → “Hi you! You've successfully authenticated” หรือโค้ดขึ้น repo ถ้ายังไม่ลงทะเบียน/ยังไม่มีกุญแจ ก้อนติดด่านแดงพร้อมข้อความบอกว่าขาดข้อไหน

เอกสารเก่าที่เก็บ view `why`/`keygen`/`register`/`connect` ยังเปิดได้ (schema แปลงเป็น `setup`; `normalizeSshView` ใช้ตอนอ่านด้วย) และฟิลด์ `known` ในสถานะเครื่องที่ถูกตัดทิ้งก็ยังผ่าน schema (ถูกลบออกตอน parse)

### ขั้น “เครื่องอื่น / กุญแจหาย” (`others`)

เพิ่มเครื่อง B (ของเพื่อน/เครื่องใหม่) และกล่อง “คนแอบคัดลอก .pub” (เลย์เอาต์ย่อเครื่อง A เพื่อให้พอ): “เครื่อง B ส่งโค้ด” → ติดด่าน (ไม่มีนิ้วที่ตรง), “คนคัดลอก .pub ลองเข้า” (6 จังหวะ) → ได้เลขสุ่มแต่ไม่มีนิ้วจริงให้แตะ → “.pub ตรวจผลสแกนได้อย่างเดียว ทำผลสแกนไม่ได้ และย้อนไปหากุญแจลับก็ไม่ได้ → เข้าไม่ได้ ✗” → ติดด่าน, “A หาย → ลบกุญแจ A” → แถวกุญแจ A จางเป็น `removed` แล้วเครื่อง A ส่งโค้ดไม่ได้, “B ลงกุญแจของตัวเอง” → B เข้าได้ (แต่ละเครื่องมีกุญแจของตัวเอง) เครื่อง B/คนแอบคัดลอกใช้ได้เฉพาะขั้นนี้ (ขั้นแรกไม่วาดจึงคืน `rejected`)

### ด้านเทคนิค

state `{ a, b: { priv, pub, cmd, out[] }, registered: ("a"|"b")[], pushes, thief }` (schema บังคับ: มี `.pub` ต้องมีกุญแจลับ, ลงทะเบียนได้เฉพาะเครื่องที่มี `.pub`) reducer `domain/ssh/reducer.ts` คืน `frames` แบบเดียวกับ Deploy; ตำแหน่งทุกจุดที่ hop/mark ใช้ต้องมีในฉากของขั้นนั้น (`ssh-layout.test.ts` ไล่ทุก action ทุกขั้นแล้วตรวจ) เส้นทางก้อนระหว่างเครื่องกับ GitHub ผ่านขอบเครื่อง → ด่านสแกน → ขอบ GitHub เสมอ, terminal ของแต่ละเครื่องแสดงคำสั่ง/ผลล่าสุด (ล้างเมื่อเปลี่ยนขั้น) การจำลองล้วน ไม่มีการเชื่อมต่อ SSH จริง

## 5. โครงสร้างทางเทคนิค (สรุป)

- **Node ใหม่ 2 ชนิด** ใน document (`data-simulator`, `deploy-simulator`) แบบเดียวกับ `git-simulator`: มี `view` (ขั้น), `scale` และ state ของตัวเอง ต้องเพิ่มใน schema, bounds/transform, export renderer และ Objects panel
- **Reducer แบบ pure ต่อ simulator:** รับ state + สถานการณ์ แล้วคืนทั้ง `nextState` และ **ลำดับจังหวะการไหล** (hops: จากกล่อง → ถึงกล่อง, ป้ายก้อน, ผลที่ด่าน, คำบรรยาย) จึงทดสอบทั้งผลลัพธ์และเส้นทางด้วย unit test ได้
- **Flow engine ร่วม:** วางกล่อง/ท่อตามขั้น, เล่น hops (session state ไม่เข้า history), ควบคุมเล่น/ทีละจังหวะ/ความเร็ว, เคารพ `prefers-reduced-motion` (แสดงคำบรรยายทีละจังหวะโดยไม่วิ่ง)
- แก้ข้อมูลตารางบนกระดานด้วย DOM overlay แบบเดียวกับกล่องไฟล์ของ Git
- ขนาด widget ตามขั้นผ่านฟังก์ชันเดียวแบบ `gitBaseSize`

## 6. ลำดับงานที่เสนอ

1. Flow engine + ตัวจำลองการเก็บข้อมูล ขั้น 1–2
2. การเก็บข้อมูล ขั้น 3–4 + ป้าย Supabase
3. ตัวจำลอง Deploy ขั้น 1–2
4. Deploy ขั้น 3–4 (ภาพรวมทั้งระบบ)

แต่ละข้อจบด้วย unit test ของ reducer/hops, e2e ทั้งสอง browser และ screenshot ทุกขั้น เหมือนงาน Git

## 7. การตัดสินใจ

- ธีมข้อมูล: ร้านกาแฟ (เมนู, ลูกค้า, ออเดอร์)
- ขั้นสิทธิ์ใช้ผู้ใช้ 2 คน: เครื่อง A = ลูกค้า #1, เครื่อง B = ลูกค้า #2
- ภาพรวมทั้งระบบอยู่ในตัวจำลอง Deploy (ขั้น 4)
- ขณะเล่น document ถูกบันทึกเป็นผลสุดท้ายทันที (หนึ่ง transaction Undo ได้) ส่วนภาพระหว่างจังหวะเป็น session state; Undo/Redo/โหลดใหม่ล้างการเล่น
- เปลี่ยนขั้นแล้วล้างหน้าจอคอมพิวเตอร์ (ผลของ action ก่อนหน้าไม่ค้างข้ามขั้น)
