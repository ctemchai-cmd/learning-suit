# 07 — ตัวจำลองการไหล: การเก็บข้อมูล และการ Deploy

> **สถานะ (2026-09-25):** ผู้สอนยืนยันแล้ว และสร้างครบทั้งสองตัว — ตัวจำลองการเก็บข้อมูล 4 ขั้น (M8.1–M8.2) และตัวจำลอง Deploy 4 ขั้น (M8.3–M8.4) ดูหลักฐานที่ [แผนส่งมอบ](06-delivery-and-acceptance.md)

## 1. เป้าหมายการสอน

ผู้สอนต้องการสอน**หลักการ** ไม่ใช่โค้ด: นักเรียนต้องเห็นว่าข้อมูลหรือโค้ด**ไหล**จากไหนไปไหน ผ่านอะไร หยุดที่ไหน และทำไม บทเรียนต่อจาก Git ตามเส้นเรื่องเดียว:

```
Git (ทำแล้ว) → การเก็บข้อมูล → Supabase (ในฐานะบริการที่เก็บข้อมูลให้) → เปิดเว็บในเครื่อง → ขึ้น Vercel → ภาพรวมทั้งระบบ
```

**ไม่ทำ:** SQL, โค้ด supabase-js, คำสั่ง terminal, การเชื่อมบริการจริง (Supabase/Vercel/GitHub) ทุกอย่างเป็นการจำลองแบบ deterministic ใช้ได้ offline, Undo ได้ และเล่นซ้ำได้ ส่วนของจริงผู้สอน demo ผ่าน dashboard ของ Supabase/Vercel แยกต่างหาก แล้วกลับมาชี้บนกระดาน

## 2. ภาษาภาพร่วม: การไหล (Flow)

ตัวจำลองทั้งสองใช้ภาษาภาพชุดเดียวกัน และใช้ engine เดียวกัน (§5)

| องค์ประกอบ | ความหมาย | ตัวอย่าง |
|---|---|---|
| **กล่อง (node)** | อุปกรณ์ บริการ หรือที่เก็บข้อมูล | มือถือลูกค้า A, ฐานข้อมูล, GitHub, Vercel |
| **ท่อ (pipe)** | เส้นทางที่ข้อมูลวิ่งได้ | มือถือ → อินเทอร์เน็ต → ฐานข้อมูล |
| **ก้อนข้อมูล (packet)** | สิ่งที่กำลังเดินทาง มีป้ายสั้น | “ออเดอร์: ลาเต้”, “โค้ดรุ่นใหม่”, “🔑 กุญแจ” |
| **ด่าน (gate)** | จุดตรวจบนท่อ ผ่าน ✓ เขียว / ไม่ผ่าน ✗ แดงแล้วก้อนเด้งกลับ | กฎสิทธิ์, ชนิดข้อมูล, Build |
| **คำบรรยาย** | หนึ่งบรรทัดใต้ภาพ บอกจังหวะปัจจุบัน | “2/4 ด่านกฎสิทธิ์: B ขอดูออเดอร์ของ A → ไม่อนุญาต” |

**แอปรอข้อมูล:** ตั้งแต่แอปส่งอะไรออกไป (หรือมีคำตอบกำลังวิ่งมาหา) จนก้อนนั้นถึง แอปขึ้นวงหมุน “กำลังโหลด…” / “กำลังบันทึก…” (`waitingAt`) รายการบนจอจึงเปลี่ยนพร้อมกับที่ก้อนถึงพอดี ใช้กับมือถือทุกขั้น และ browser ในเครื่อง/มือถือเพื่อนของตัวจำลอง Deploy

**การควบคุมของผู้สอน (แผงขวา):** ปุ่มสถานการณ์ของขั้นนั้น (เช่น “ลูกค้า A สั่งลาเต้”), เล่นต่อเนื่อง / **ทีละจังหวะ** (ปุ่ม “ถัดไป ▶” เพื่อหยุดอธิบายแต่ละช่วง), ความเร็ว ช้า/ปกติ และเล่นซ้ำ ระหว่างเล่นยังไม่แก้ document; จบจังหวะสุดท้ายผลลัพธ์ (แถวใหม่, deployment ใหม่) บันทึกเป็น **transaction เดียว Undo ได้** เหมือน action ของ Git

**แผงขวาต้องคลีน (feedback 2026-09-26):** หัวข้อสั้นหนึ่งบรรทัดต่อเรื่อง, ตัวเลือกเป็น segmented control, ปุ่มสถานการณ์มีไอคอนและคำสั้น (ปุ่มแรกที่ควรลองเป็นสีน้ำเงิน), ฟอร์มหลายแบบแยกเป็นแท็บ (เช่น เพิ่ม/ดู/แก้/ลบ) ไม่มีคำอธิบายซ้ำกับกระดาน — คำอธิบายอยู่ในแถบคำบรรยายบนกระดาน, คำอธิบายขั้นอยู่ใน tooltip ของ dropdown; แถบควบคุมการเล่นย่อเหลือ “ต่อเนื่อง/ทีละจังหวะ” + ปุ่มช้า และแสดงความคืบหน้า/ถัดไป/ข้าม/เล่นซ้ำเฉพาะตอนกำลังเล่น เมนูที่สั่งหมุนเวียนเองจึงไม่ต้องเลือก

**กติกาที่ยกมาจากตัวจำลอง Git:** ขั้นบทเรียนเลือกจาก dropdown แต่ละขั้นเพิ่มแนวคิดใหม่เรื่องเดียว; แก้ข้อมูลบนกระดานได้โดยตรง; แผงขวามีแค่ปุ่มและไฮไลต์ “ทำต่อ”; ความผิดพลาดที่พบบ่อยจำลองได้และ**ต้องมีทางออกเสมอ**; Export เป็นภาพนิ่งของสถานะล่าสุด (ไม่มีก้อนที่กำลังวิ่ง); ป้ายเล็ก “ใน Supabase/Vercel เรียกว่า …” เชื่อมไปของจริงโดยไม่ต้องเห็นโค้ด

## 3. ตัวจำลองการเก็บข้อมูล (ธีมร้านกาแฟ)

ข้อมูลตัวอย่าง: ตาราง **เมนู** (ชื่อ, ราคา), **ลูกค้า** (ชื่อ), **ออเดอร์** (ลูกค้า → , เมนู → , จำนวน) แก้ทุกช่องบนกระดานได้

### ขั้น 1 — ข้อมูลเก็บที่ไหน

มือถือแต่ละเครื่องวาดเป็น **หน้าต่างแอป** (แถบชื่อ + ไอคอนรีเฟรช ↻) ที่มี **ความจำของแอปอยู่ในกรอบของแอป** ส่วน “เก็บในเครื่อง” อยู่ในมือถือแต่อยู่นอกแอป รีเฟรช = แอปเริ่มใหม่: ↻ หมุน หน้าจอว่าง ความจำของแอปลอยหาย แล้วจึงโหลดใหม่ตามวิธีเก็บ

กล่อง: มือถือ A, มือถือ B, ฐานข้อมูล (cloud) สถานการณ์ “A สั่งลาเต้” เล่นได้สามแบบ:

```
เก็บในแอป        A: [ลาเต้] ─ รีเฟรช → 💨 หาย                      ✗
เก็บในเครื่อง A   A: [ลาเต้]    B เปิดดู → (ว่าง) มองไม่เห็นของ A    ✗
เก็บในฐานข้อมูล   A ──ลาเต้──▶ [ฐานข้อมูล] ──ลาเต้──▶ B              ✓ ทุกเครื่องเห็นเหมือนกัน
```

### ขั้น 2 — ตาราง

ฐานข้อมูลขยายเป็นตาราง: 1 แถว = 1 ชิ้นข้อมูล, 1 คอลัมน์ = 1 เรื่อง, ทุกแถวมีเลข ID ไม่ซ้ำ และแต่ละคอลัมน์มีชนิดข้อมูล (ข้อความ / ตัวเลข / ใช่-ไม่ใช่ / วันที่) สถานการณ์สี่แบบแสดงเป็นการไหล:

- **เพิ่ม** (Create): ก้อนวิ่งเข้าไป แถวใหม่ค่อยๆ ปรากฏ
- **ดู** (Read): สำเนาแถววิ่งกลับไปที่มือถือ ตารางเดิมไม่เปลี่ยน
- **แก้** (Update): ก้อนวิ่งไปหยุดที่ช่องเดียว ช่องนั้นเรืองแสงเป็นค่าใหม่
- **ลบ** (Delete): แถวจางหายไป
- ใส่ “ห้าสิบ” ในช่องราคา: ก้อนติดด่าน “ชนิดข้อมูล” สีแดงแล้วเด้งกลับ ตารางไม่เปลี่ยน

### ขั้น 3 — เชื่อมตาราง (อย่าก๊อปข้อมูลซ้ำ)

วางสองวิธีคู่กัน แล้วเล่นสถานการณ์ “ลูกค้าเปลี่ยนชื่อ”:

```
ก๊อปชื่อไว้ในทุกออเดอร์                  อ้างถึงด้วย ID
ออเดอร์ 1: "สมชาย"                      ออเดอร์ 1 ─┐
ออเดอร์ 2: "สมชาย"   ← ต้องแก้ทุกแถว       ออเดอร์ 2 ─┴─▶ ลูกค้า #7 "สมชาย" ← แก้ที่เดียว
ลืมแก้บางแถว → ชื่อขัดกัน ✗ (สีแดง)       ทุกออเดอร์ตามเส้นไปเห็นชื่อใหม่ ✓
```

ลบลูกค้าที่ยังมีออเดอร์: ก้อนติดด่าน “ยังมีข้อมูลอ้างถึง (2 ออเดอร์)” พร้อมทางออก: ลบออเดอร์ก่อน หรือยกเลิก

### ขั้น 4 — ใครเห็นอะไร (สิทธิ์)

มือถือ A และ B login เป็นคนละคน คำขอทุกครั้งต้องผ่านด่าน **กฎสิทธิ์** ก่อนถึงตาราง:

```
B: ขอดูออเดอร์ ──▶ [ด่านกฎสิทธิ์: เห็นเฉพาะของตัวเอง] ──▶ ออเดอร์ของ B ✓
                                                   ออเดอร์ของ A ✗ (ถูกกรองที่ด่าน)
เมนู = ข้อมูลสาธารณะ ทุกคนเห็น
ปิดกฎสิทธิ์ → ออเดอร์ของ A วิ่งถึง B เป็นสีแดง “ข้อมูลรั่ว”
```

### ป้ายเชื่อมกับ Supabase (ไม่มีโค้ด)

ฐานข้อมูล = **Supabase (Postgres)**, ตาราง = **Table Editor**, คนที่ login = **Authentication**, กฎสิทธิ์ = **RLS Policy**, ท่อจากแอปถึงฐานข้อมูล = **API** ผู้สอนเปิด dashboard ของ Supabase ให้เห็นว่าเป็นสิ่งเดียวกัน (สร้างตาราง/นโยบายได้จากหน้าเว็บโดยไม่เขียนโค้ด)

## 4. ตัวจำลองการ Deploy

กล่อง: เครื่องเรา (โค้ด), เซิร์ฟเวอร์ในเครื่อง, GitHub, Vercel (ด่าน Build → Deploy), อินเทอร์เน็ต, มือถือเพื่อน และในขั้นท้าย Supabase ไม่แสดงคำสั่ง แสดงเป็นปุ่มภาษาคน เช่น “เปิดเว็บในเครื่อง”, “ส่งโค้ดขึ้น GitHub”

### ขั้น 1 — เปิดเว็บในเครื่อง (Local)

```
[โค้ด] ──▶ [เซิร์ฟเวอร์ในเครื่อง] ──▶ [browser ในเครื่อง: localhost] ✓
[มือถือเพื่อน] ──✗── ท่อขาด “ที่อยู่นี้มีแค่ในเครื่องเรา”
แก้โค้ด → ก้อน “โค้ดใหม่” วิ่งไปเซิร์ฟเวอร์ → หน้าเว็บในเครื่องเปลี่ยนทันที
```

### ขั้น 2 — กุญแจในเครื่อง (.env.local)

```
[.env.local 🔑] ──กุญแจ──▶ [เซิร์ฟเวอร์ในเครื่อง] ──🔑 ออเดอร์──▶ [ฐานข้อมูล]  ✓
เอากุญแจออก → เซิร์ฟเวอร์หากุญแจไม่เจอ → ต่อฐานข้อมูลไม่ได้ ✗
```

เห็นภาพ env ในเครื่องอย่างเดียวก่อนขึ้น Vercel: ไฟล์ลับอยู่ในเครื่อง เซิร์ฟเวอร์อ่านกุญแจทุกครั้งที่ต้องคุยกับฐานข้อมูล สลับ “มีกุญแจ / ไม่มี” ได้จากแผง

### ขั้น 3 — ขึ้น Vercel

```
[เครื่องเรา] ──โค้ด──▶ [GitHub] ──▶ [Vercel: ด่าน Build ✓ → Deploy] ──▶ [URL สาธารณะ] ◀── มือถือเพื่อน ✓
```

- ทุกครั้งที่ส่งโค้ดขึ้น GitHub จะเกิด deployment ใหม่ (D1, D2 …) หน้าตาเหมือนรายการ commit และมีป้าย “ใช้งานจริง (Production)” เหมือนป้าย main
- **Build ล้ม:** ก้อนหยุดที่ด่าน Build เป็นสีแดง แต่**เว็บเดิมยังออนไลน์อยู่** (ป้าย Production ไม่ย้าย) เป็นบทเรียนสำคัญ
- **ย้อนรุ่น (Rollback):** ย้ายป้าย Production กลับไป deployment ก่อนหน้า มือถือเพื่อนเห็นรุ่นเก่าทันที

### ขั้น 4 — กุญแจบน Vercel

```
[เครื่องเรา: 🔑 กุญแจฐานข้อมูล] ──โค้ด──▶ GitHub      (กุญแจไม่ถูกส่งไปด้วย: ติดด่าน “ไฟล์ลับ”)
[Vercel: ตั้งค่า 🔑] ← ผู้สอนต้องใส่เองในหน้าตั้งค่า
ลืมใส่ → เว็บออนไลน์ แต่ท่อ Vercel → Supabase ขาด “ต่อฐานข้อมูลไม่ได้” ✗
ใส่แล้ว Deploy ใหม่ → ต่อได้ ✓
```

### ขั้น 5 — ภาพรวมทั้งระบบ

มือถือเพื่อนสั่งกาแฟบนเว็บจริง: มือถือ → Vercel → Supabase (ด่านกฎสิทธิ์) → ตารางออเดอร์ → ผลวิ่งกลับ รวมทุกบทเรียนไว้ในภาพเดียว ตรงกับที่นักเรียนจะทำจริงและตรงกับแอปนี้เองที่ใช้ Vercel + Supabase

เพราะทุกขั้นใช้ state เดียวกัน การทดลองในขั้นก่อน (เช่น ทำโค้ดพัง หรือยังไม่ใส่กุญแจ) จะติดมาด้วย ขั้นนี้จึงมีปุ่ม **“เตรียมเว็บให้พร้อม”** ที่แก้โค้ด + ใส่กุญแจ + Deploy ต่อกันเป็น flow เดียว (Undo ได้ในครั้งเดียว) ส่วนขั้นกุญแจลับมีการ์ดแก้โค้ดเมื่อโค้ดยังพังค้างอยู่

## 4b. ตัวจำลอง AI (เพิ่ม 2026-09-26)

ผู้สอนขอ: สอนการทำงานของ AI, Memory, เทียบ AI บนเว็บกับ Claude Code, ความจำที่ Claude ใช้, การรับส่งข้อมูล (ทำไม AI รู้ประวัติแชท) และ Chain of Thought — **จำลองล้วน ไม่เรียก AI จริง** และไม่ลงลึกถึง “เดาคำถัดไป” node `ai-simulator` ใช้ flow engine เดียวกับข้อมูล/Deploy (กรอบ 1120×680, ก้อนข้อมูลบนท่อ, คำบรรยาย, เล่นต่อเนื่อง/ทีละจังหวะ) คำตอบมาจากกฎตายตัวใน `domain/ai/chat.ts` (หา “ชื่อ/อาชีพ/ชอบ” ในประโยคไทย แล้วตอบจากข้อมูลที่ “ได้รับ” เท่านั้น) บนกระดานมีป้าย “จำลอง · ไม่ได้เรียก AI จริง”

| ขั้น | เห็นอะไร | ปุ่ม |

## 5. โครงสร้างทางเทคนิค (สรุป)

- **Node ใหม่ 2 ชนิด** ใน document (`data-simulator`, `deploy-simulator`) แบบเดียวกับ `git-simulator`: มี `view` (ขั้น), `scale` และ state ของตัวเอง ต้องเพิ่มใน schema, bounds/transform, export renderer และ Objects panel
- **Reducer แบบ pure ต่อ simulator:** รับ state + สถานการณ์ แล้วคืนทั้ง `nextState` และ **ลำดับจังหวะการไหล** (hops: จากกล่อง → ถึงกล่อง, ป้ายก้อน, ผลที่ด่าน, คำบรรยาย) จึงทดสอบทั้งผลลัพธ์และเส้นทางด้วย unit test ได้
- **Flow engine ร่วม:** วางกล่อง/ท่อตามขั้น, เล่น hops (session state ไม่เข้า history), ควบคุมเล่น/ทีละจังหวะ/ความเร็ว, เคารพ `prefers-reduced-motion` (แสดงคำบรรยายทีละจังหวะโดยไม่วิ่ง)
- แก้ข้อมูลตารางบนกระดานด้วย DOM overlay แบบเดียวกับกล่องไฟล์ของ Git
- ขนาด widget ตามขั้นผ่านฟังก์ชันเดียวแบบ `gitBaseSize`

## 6. ลำดับงานที่เสนอ

1. Flow engine + ตัวจำลองการเก็บข้อมูล ขั้น 1–2
2. การเก็บข้อมูล ขั้น 3–4 + ป้าย Supabase
3. ตัวจำลอง Deploy ขั้น 1–2
4. Deploy ขั้น 3–4 (ภาพรวมทั้งระบบ)

แต่ละข้อจบด้วย unit test ของ reducer/hops, e2e ทั้งสอง browser และ screenshot ทุกขั้น เหมือนงาน Git

## 7. การตัดสินใจ

- ธีมข้อมูล: ร้านกาแฟ (เมนู, ลูกค้า, ออเดอร์)
- ขั้นสิทธิ์ใช้ผู้ใช้ 2 คน: เครื่อง A = ลูกค้า #1, เครื่อง B = ลูกค้า #2
- ภาพรวมทั้งระบบอยู่ในตัวจำลอง Deploy (ขั้น 4)
- ขณะเล่น document ถูกบันทึกเป็นผลสุดท้ายทันที (หนึ่ง transaction Undo ได้) ส่วนภาพระหว่างจังหวะเป็น session state; Undo/Redo/โหลดใหม่ล้างการเล่น
- เปลี่ยนขั้นแล้วล้างหน้าจอมือถือ (ผลของ action ก่อนหน้าไม่ค้างข้ามขั้น)
